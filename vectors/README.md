# Cross-language test vectors

Generated by `tools/gen_vectors.py`. Do not edit by hand; regenerate with:

```bash
source ~/env/py/ebus/bin/activate   # has numpy 2.2.6, paho-mqtt and zeroconf
cd /Users/dcj/projects/eBus/repo
PYTHONPATH=python-sdk/src:ebus-mqtt-client/src:python-service-discovery/src python3 rust-sdk/tools/gen_vectors.py
```

Output is deterministic (fixed seeds, fixed corpus order).

The spec suites express the Homie 5 convention and the eBus specification. Where python-sdk (`python-sdk/src/ebus_sdk/homie.py`) has a matching function, its result is the expect value, except where python-sdk deviates from the convention ([python-sdk#110](https://github.com/electrification-bus/python-sdk/issues/110)): those cases are listed in `CONVENTION_OVERRIDES` in the generator, each with the convention's expect and a `source` citing the convention line and python-sdk#110.

The python-service-discovery suites (`python-service-discovery/`) record [python-service-discovery](https://github.com/electrification-bus/python-service-discovery)'s implementation of the eBus DNS-SD contract (framework.md, "Detail: mDNS Discovery"), where the spec leaves a choice open. The harness is `crates/ebus-discovery/tests/vectors.rs`.

The python-sdk suites (`python-sdk/`) record python-sdk's behavior where the spec leaves a choice open, except `float32-format.json`, which records rust-sdk's `f32` choice: numpy's shortest `float32` digits in the layout of python-sdk's `_format_float`. They are not spec requirements: rust-sdk prefers python-sdk's choice but may differ where matching it is costly.

## File format

Every file follows electrification-bus/specification#33:

```json
{
  "$schema": "https://ebus.energy/schemas/conformance-vectors.json",
  "suite": "payloads/integer",
  "version": "0.1",
  "generator": "rust-sdk tools/gen_vectors.py from python-sdk 0.26.0",
  "cases": [{"id": "...", "source": "...", "input": {...}, "expect": {...}}]
}
```

`id` is unique within a file. `source` cites the rule or the Python function that produced `expect`; when it says "derived from the convention", the expectation was written from `convention.md`. A payload is either `payload` (UTF-8 text) or `payload_hex` (raw bytes as lowercase hex; used for zero-length payloads, payloads containing `0x00`, and invalid UTF-8). A harness decodes `payload_hex` to bytes, and for text-level APIs converts those bytes to `&str` (all `payload_hex` values in the payload suites are valid UTF-8).

Floats are written as Python `repr` (shortest round-trip digits), so a reader must round correctly to get the f64 Python used. `serde_json` does that only with its `float_roundtrip` feature, which `crates/ebus-homie/Cargo.toml` does not enable; the Rust harness reads the files with `ebus_homie::pyfmt::from_json`, which rounds correctly. Integers fit in `i64` or `u64`, and objects are read in key order (`serde_json` without `preserve_order`). `python-sdk/set-payload.json` also carries exact bits for float `current` values.

## Spec suites

### `topics.json`

- input: `{"topic": string}`
- expect, accepted: `{"valid": true, "domain": string, "device": string | null, "kind": string, ...fields}`. `device` is `null` only for `Broadcast`. `kind` is the `TopicKind` variant name, with these extra fields:
  - `DeviceState`, `DeviceDescription`: none
  - `DeviceLog`: `"level"` (one of `debug`, `info`, `warn`, `error`, `fatal`)
  - `DeviceAlert`: `"alert_id"`
  - `PropertyValue`, `PropertySet`, `PropertyTarget`: `"node"`, `"property"`
  - `Broadcast`: `"subtopic"` (everything after `$broadcast/`, may contain `/`)
- expect, rejected: `{"valid": false, "error": string}`. `error` is a non-normative camelCase hint (`badVersion`, `invalidDomain`, `invalidDeviceId`, `tooShort`, `unknownAttribute`, `unexpectedLevel`, `missingLogLevel`, `unknownLogLevel`, `missingAlertId`, `invalidAlertId`, `invalidNodeId`, `invalidPropertyId`, `missingSubtopic`, `invalidSubtopic`); a harness asserts only that parsing fails.
- Rules applied: every level is a valid id (`[a-z0-9-]+`) except the reserved `$` attributes; the version level is exactly `5`; the domain is a valid id; device attributes are `$state`, `$description`, `$log/<level>`, `$alert/<id>`; property topics are `<node>/<prop>`, `<node>/<prop>/set`, `<node>/<prop>/$target`; the device base topic and node base topic are not message topics.

### `empty-string.json`

Three input shapes, selected by `direction`:

- `"decode"`: input `{"direction": "decode", "topic_kind": "value" | "set" | "target", "datatype": "string", "payload_hex": hex}` (or `payload`). Expect one of:
  - `{"deleted": true}`: zero-length payload (topic deletion; `payload::classify` returns `Received::Deleted`).
  - `{"deleted": false, "value": string}`: the decoded string value (`[0x00]` decodes to `""`; any other payload, including `00 00`, passes through unchanged).
  - `{"error": "invalidUtf8"}`: the bytes are not UTF-8.
- `"encode"`: input `{"direction": "encode", "datatype": "string", "value": string}`; expect `{"payload_hex": hex}` (`""` encodes to `00`).
- `"set"`: input `{"direction": "set", "datatype": string, "payload_hex": "00", "format"?: string}`; expect `{"valid": false, "problem": string}`, the `Problem::as_str()` that `parse_set_payload("\0", datatype, format, None)` must return. A lone `0x00` is the empty string only for `string`.

### `effective-state.json`

- input: `{"has_root": bool, "root_state": string | null, "own_state": string}` (`root_state` is `null` exactly when `has_root` is false).
- expect: `{"state": string}`.
- Maps to `state::effective_state(if has_root { Some(root) } else { None }, own)`. All 25 root/own combinations plus 5 no-root cases. Derived from the convention's table (convention.md:262-267): a root in `lost` makes the device `lost`; otherwise the device's own state stands. python-sdk's `HOMIE_EFFECTIVE_STATE_TABLE` also propagates a root's `init`, `disconnected` and `sleeping` (python-sdk#110 item 1).

### `payloads/<datatype>.json` (integer, float, boolean, string, enum, color, datetime, duration, json)

- input: `{"datatype": string, "payload": string | "payload_hex": hex, "format"?: string}`. `format` absent means `None`.
- expect, accepted: `{"valid": true, "value": V}` where `V` is what `parse_set_payload(text, datatype, format, None)` returns: for `json`, the decoded JSON value (compare as `serde_json::Value`); for `string`, the decoded text (`0x00` gives `""`); for every other datatype, the normalized payload text (`SetValue::Text`). Numbers are text, not JSON numbers.
- expect, rejected: `{"valid": false, "problem": string}`, compared with `Problem::as_str()`.
- Convention rules python-sdk does not apply (python-sdk#110): an `integer` that step rounding takes outside the 64-bit range is `integerOutOf64Bit`; a `datetime` with hour `24` other than the end of a day (`T24`, `T24:00`, `T24:00:00`, zero fraction), ordinal day `366` in a common year, or week `53` in a year with 52 ISO weeks is `datetimeRange` (ISO 8601-1, which convention.md:132 defers to); a `json` number that overflows to an infinity or a lone surrogate escape is `jsonInvalid`.

### `description.json`

- input: `{"payload": string}`: the `$description` document as text (sometimes not JSON, or not an object).
- expect: `{"valid": true}`, `{"valid": true, "ignored": [{"node": string, "property": string | null, "error": string}]}`, or `{"valid": false, "error": string}`. `ignored` lists, in order, the nodes (`property` null) and properties that `description::parse_with_ignored` leaves out of an accepted document; nothing else is left out. `error` is a non-normative camelCase hint; a harness asserts only that parsing fails, or which entries are ignored.
- Rules applied (convention.md:210-222, :300-306, :336-345, :383-395, :659-668): `homie` required, a string `"5.<digits>"`; `version` required, a JSON integer in the `i64` or `u64` range; `name` and `type` strings when present (not nullable); `nodes` an object; `children` an array of valid id strings; `root`/`parent` valid id strings, `parent` only with `root`; `extensions` an array of strings. A device-level violation rejects the document. A node is ignored when its id is not a valid id, it is not an object, its `name` or `type` is not a string, or its `properties` is not an object. A property is ignored when its id is not a valid id, it is not an object, its `datatype` is missing or not one of the 9 names, `settable`/`retained` are not booleans, `format`/`unit`/`name` are not strings, or its format is illegal: `enum` and `color` need a non-empty `format`; enum values are non-empty and distinct; color types are `rgb`, `hsv`, `xyz`; a non-empty boolean format has 2 distinct non-empty entries; a non-empty integer or float format is `[min]:[max][:step]` with bounds in the datatype's payload form and a step > 0. Unknown fields at any level are ignored.

### `check-value.json`

- input: `{"datatype": string, "payload": string | "payload_hex": hex, "format"?: string}`: a received property value or `$target` as wire bytes. A `""` value arrives as `payload_hex` `00`; no case is zero-length. `format` absent means `None`.
- expect: `{"valid": true}` or `{"valid": false, "problem": string}`, compared with `Problem::as_str()`.
- Maps to `datatype::check_value(text, &property)`, where `text` is `payload::classify(bytes)`'s `Received::Text` and `property` is `PropertyDescription::new(datatype)` with `format`.
- Rules applied: the payload suites' rules with no step rounding, since rounding is the device's job (convention.md:399): a value off the step is valid and one beyond min or max is `belowMin` or `aboveMax` even where rounding would bring it in range. `0x00` is valid only for `string`. Expect values are python-sdk `_parse_set_payload` on the decoded text with the step removed from `format`, except the `datetime` and `json` cases of `CONVENTION_OVERRIDES` (python-sdk#110). Where python-sdk's `_parse_set_payload` with the step gives a different verdict, the case's `source` records it.

## python-sdk suites (`python-sdk/`)

### `python-sdk/float-format.json`

- input: `{"f64_bits": string, "repr_hint": string}`. `f64_bits` is the IEEE 754 bit pattern as 16 lowercase hex digits (big-endian, `f64::from_bits(u64::from_str_radix(bits, 16))`). `repr_hint` is Python's `repr()` for humans; do not parse it.
- expect: `{"payload": string | null}`: `pyfmt::format_float(x)`; `null` for NaN and the infinities.

### `python-sdk/float32-format.json`

- input: `{"f32_bits": string, "repr_hint": string}`. `f32_bits` is the IEEE 754 bit pattern as 8 lowercase hex digits (big-endian, `f32::from_bits(u32::from_str_radix(bits, 16))`). `repr_hint` is numpy's `str()` for humans; do not parse it.
- expect: `{"payload": string | null}`: `pyfmt::format_float32(x)`: numpy's shortest round-trip `float32` digits (`21.4`, not the widened f64's `21.399999618530273`) in the layout of `python-sdk/float-format.json`; `null` for NaN and the infinities.

### `python-sdk/sanitize-id.json`

- input: `{"value": string}`; expect: `{"id": string}` = `id::sanitize_id(value)`.

### `python-sdk/set-payload.json`

- input: `{"datatype": string, "payload": string | "payload_hex": hex, "format": string | null, "current": number | null, "current_f64_bits"?: string}`. `current` is the property's current value: a JSON integer is an integer current, a JSON number with a fraction or exponent is a float current, and then `current_f64_bits` gives its exact bits (same encoding as float-format). `datatype` may be an unknown name (`"number"`): Python treats it as `string`.
- expect: `{"ok": V}` (same `V` rules as the payload suites) or `{"problem": string}`.

### `python-sdk/json-dumps.json`

- input: `{"json": string}`: JSON text; parse with `serde_json::from_str::<Value>`. Object keys are unique and integers fit in i64/u64, so the parsed value is exactly what Python parsed.
- expect: `{"text": string}` = Python `json.dumps(value, sort_keys=True)` = `pyfmt::to_json(&value, true)`.
- Floats in this output use Python `float.__repr__`, which keeps the `+` in exponents (`1e+16`, `1.5e+300`) and pads to two exponent digits (`1e-05`). That is not `format_float` (which removes `e+`).

### `python-sdk/encode-duration.json`

- input: `{"total_seconds": u64, "microseconds": u32}` (`microseconds < 1_000_000`); expect: `{"payload": string}` = `datatype::encode_duration(total_seconds, microseconds)`.

### `python-sdk/description-wire.json`

One case per device in each Python-built tree (a tree's children get their own cases). Case id: `description-wire-<tree>-<device id>`.

Input: a structural description that maps field-for-field onto `DeviceDescription`:

```json
{
  "id": "light1",
  "name": "First light",
  "type": null,
  "nodes": [
    {
      "id": "n",
      "name": "n",
      "type": null,
      "properties": [
        {"id": "p", "name": "p", "datatype": "float", "format": null, "settable": false, "retained": true, "unit": null}
      ]
    }
  ],
  "children": [],
  "root": "bridge",
  "parent": "dualrelay",
  "extensions": ["x.y.z"],
  "extras": [["key", <any JSON value>]]
}
```

Input fields:

- `id` is the device id (not serialized; for naming only).
- `name` (device, node and property) is always a string: the name Python emits, already defaulted to the id.
- `type` (device and node) is a string or `null`; `null` means `None` (omitted on the wire), while `""` is `Some("")` and is emitted.
- `nodes` and `properties` are arrays in document order (use them in order for `Vec<(String, _)>`).
- `format` is a string or `null`. A JSON-schema format arrives already encoded as the string Python wrote. `""` must be omitted on the wire, like `null`.
- `unit` is a string or `null`; `""` is omitted on the wire, like `null`.
- `children` is in creation order; `root` and `parent` are `null` for a root device and both set for every child (Python always emits `parent`, even when it equals `root`).
- `extras` is an ordered array of `[key, value]` pairs exactly as passed to Python, including core keys (`name`, `root`, `type`, ...) that the serializer must drop. Nested objects inside extras values have their keys in sorted order, so `serde_json` (BTreeMap) iteration order matches Python's insertion order.

Expect: `{"wire": string, "version": u64, "content_hash_hex": string}`. `wire` is the exact `json.dumps(device.description())` text, byte for byte (`DeviceDescription { version, .. }.to_json()` with `version` set to the expected value, or `with_computed_version().to_json()`). `version` is `compute_version()`. `content_hash_hex` is the lowercase hex of `content_hash()`. Floats in extras serialize with Python `repr` (`1e+16`), as in json-dumps.

### `python-sdk/description-roundtrip.json`

One case per device in each description-wire tree, plus trees whose node, property, extra and child ids are all out of alphabetical order (`zeta`, `alpha`, `mid`). Case id: `description-roundtrip-<tree>-<device id>`.

- input: `{"payload": string}`: Python `json.dumps(Device.description())`.
- expect: `{"wire": string}`, equal to `payload`. `description::parse_with_ignored(payload)` must accept it, leave nothing out, and `to_json()` must reproduce it byte for byte, so nodes, properties and top-level extras must be read in document order. Nested objects inside extras values have sorted keys, as in description-wire.

## python-service-discovery suites (`python-service-discovery/`)

TXT strings are given as `strings` (UTF-8) or `strings_hex` (hex of each string's bytes), in record order. Python's expect values come from python-zeroconf's TXT parse followed by `decode_txt`, as a direct browse receives them. A case whose `source` starts with `rust-sdk` records rust-sdk's rule from [doc/design.md](../doc/design.md) where it differs from python; the generator fails if python comes to agree. An instance is `{"service_type", "instance_name", "server", "port", "txt": [[key, value]], "addresses": [string]}`; an address may carry a numeric zone (`fe80::2%2`), the interface index. Addresses that tie on scope preference are listed in address order, since rust-sdk breaks ties by address and python's sort is stable. An endpoint in an expect is `{"url", "instance"}`.

|---|---|---|---|
| `decode-txt` | TXT strings | `{"txt": [[key, value]]}` | `TxtRecord::from_strings`, then `get` per key in order. rust-sdk cases: the first of keys equal ignoring case wins, and a string with an empty key is skipped |
| `parse-ebus-txt` | TXT strings | `txtvers`, `ebus_version`, `roles`, `device_ids`, `auth_methods`, `missing`, `is_broker_host` | `parse_ebus_txt` |
| `check-txt` | `{"service_type", "txt": [[key, value]]}` | `{"valid": false}` or `{"valid": true, "long_keys", "large"}` | `check_txt`; `long_keys` are `TxtReport::long_strings` keys, `large` is `TxtReport::is_large` |
| `service-txt` | `record`: `identity`, `http` or `broker`, with the identity's fields and the service's | Ordered TXT pairs, or `{"error": true}` | `Identity::check`, `ebus_txt`, `device_info_txt`; `HttpService::txt`; `BrokerService::txt` |
| `broker-endpoint` | An instance | The endpoint's fields, `url` and candidate `addrs` | `BrokerEndpoint::from_instance` |
